# Staff scheduling UI — Stage 3 implementation plan

> **For implementation:** Read [01-spec.md](01-spec.md) and [02-design.md](02-design.md) before each affected task. Execute the checked steps in order, testing each deliverable before moving on. This document authorizes no implementation; await manager review.

**Goal:** Replace the NiceGUI landing scaffold with the approved, roster-first manager workflow and add the read-only manual-edit previews and version gates it requires.

**Architecture:** `ScheduleService` remains the source of truth for persistence, eligibility, warnings, and metrics. One NiceGUI page controller holds the selected ID, last committed `ScheduleResult`, transient editors/proposals, history mode, epoch, and busy state. UI modules render service records and send stable IDs and version-bound proposals back to the service.

**Tech stack:** Python 3.10+, NiceGUI 3.18.0, SQLite, pytest, Ruff; no new dependency or schema migration.

## 1. Implementation summary based on the approved design

- Build one page at `/` with a compact schedule/settings/summary header, a Monday–Sunday shift grid as the primary view, and reachable staff, shifts, demand, hourly analysis, warnings, and read-only history panels. Sort shift rows by `(start_hour, end_hour, id)`; show actual time ranges and every assignee in each cell.
- Persist only the last selected schedule ID in browser `localStorage`. On every page open, compare it with `list_schedules`; select the first schedule in creation order when invalid or absent. Keep all schedule data in SQLite and load it with `get_schedule`. A selection change or entry into history clears transient editors and pending proposals. Another open tab keeps its current page-local selection until that tab is reloaded or the manager switches it.
- Add typed, read-only `preview_assignment_options` and `preview_shift_edit` results in `src/model/scheduling.py` and `ScheduleService`. Reuse existing `validate_state`, `calculate_result`, and boundary validation. Add optional `expected_version` to add/reassign assignment, edit shift, and confirmed staff/shift removal; check it under the write transaction before any mutation. Existing callers without the argument retain their behavior.
- Use service responses as atomic UI updates. For initial import, call `validate_import` then `import_initial`; for re-import or a post-import threshold change, keep the exact proposal with its signed `preview_refresh` token until `confirm_refresh`. Use `generate` for an empty roster and preview/confirm generation for a nonempty one. Show historical snapshots from the saved payload without recalculating or offering restore.
- Validate browser fields as boundary values, cap CSV uploads at 1 MiB before/while reading, and display structured service errors and findings. Use NiceGUI text/value controls for untrusted content. Offload potentially slow synchronous service calls so busy feedback can render; discard a late response when the page's selected schedule or selection epoch has changed.
- **Scope:** implement FR-1–FR-13 and the five non-functional requirements in the approved UI spec. No policy change, schema migration, publication, authentication, drag-and-drop, export, snapshot restore, or new package. `main.py` and the sample CSV remain unchanged.

## 6. Implementation risks and assumptions

- **No flagged conflict or dependency:** The steps follow the approved design and `AGENTS.md`; no new dependency, schema migration, source-document edit, sample-CSV edit, generated-file edit, or main-branch push is required. If implementation discovers a need for any of those, stop that step for review rather than silently expanding scope.
- **Manager decision:** Browser `localStorage` holds the approved browser-scoped selected ID. Treat its value as untrusted; only a positive ID present in `list_schedules` may be loaded. A selection change in one tab updates the saved preference but does not switch another already-open tab; that tab changes only on its own reload or explicit selection. A later page open reads the latest saved ID. No schedule data, upload bytes, preview token, or secret goes into browser storage.
- NiceGUI 3.18.0 exposes `user_simulation`, `ui.upload.handle_uploads`, and asynchronous `FileUpload.iterate()`. Integration tests can use them without a package addition. The simulator cannot prove actual focus movement, scroll behavior, or responsive legibility, so the final browser check is necessary.
- Service preview performance can grow with employee count because each allowed option needs projected metrics. Keep one SQLite read per cell and do projections in memory; measure a 100-employee case before assuming the UI is responsive. Avoid recalculating in the renderer.
- A used-shift edit or confirmed deletion requires a fresh versioned preview/count. A concurrent change can invalidate it; show `STALE_PREVIEW`, reload, and require a new review. Never send a changed CSV/threshold with an old token.
- Untrusted upload size is checked before and during byte collection; `ui.upload` client size limits are convenience only. The service remains the authoritative parser for UTF-8, shape, complete 112 cells, and integer ranges. Do not render uploaded strings through HTML or log report contents.
- `ScheduleResult.roster` and `hourly` already contain sorted slots and all 112 hours; `ScheduleState.demand is None` is the unavailable marker. `0` transactions are valid. Historical snapshots already carry captured analytics, so historical views must render them directly.
- Current planning-session pytest fixture setup is blocked by sandbox temp-directory permissions. The implementation's definition of done still requires every applicable `AGENTS.md` check to pass in an environment with writable temp storage; do not waive the gate or reinterpret fixture errors as product failures.
