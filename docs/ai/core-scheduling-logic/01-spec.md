# Core scheduling logic — Stage 1 specification

**Task:** `core-scheduling-logic`  
**Authority:** [Staff Scheduling System BRD](../../resources/Staff_Scheduling_System_BRD.md), especially BR-01–BR-10, Sections 5, 7, and 9. The [take-home assignment](../../resources/SWE_Take-Home_Staff_Scheduling_System.pdf) supplies context. The manager's decisions recorded in Section 6 explicitly supersede the BRD's retain-roster rule for confirmed demand re-imports and threshold changes; the source documents are unchanged.  
**Status:** Proposed for manager review. This document specifies behavior; it does not claim the behavior is implemented.

## 1. Goal and non-goals

Specify the business logic that lets a manager create an independent, reusable Monday–Sunday schedule, import hourly demand, maintain staff and shifts, generate a valid demand-aware draft, edit assignments, preserve prior states for historical analytics during confirmed demand/settings refreshes, and inspect truthful coverage and workload measures. The same rules must be callable without a browser and testable with pure domain tests and temporary SQLite databases.

The existing repository only persists named schedules. `src/domain/periods.py` defines weekdays, default shifts, and a generic same-day `shift_hours` helper; `src/domain/schedules.py` validates 1–100-character schedule names; `src/model/schedule.py`, `src/db/`, and `src/services/schedules.py` cover schedule name records; `ui/app.py` is a scaffold page. Current tests cover those boundaries only. New logic should extend these layers while preserving their existing behavior. In particular, the new *shift-definition* rule of 07:00–23:00 must not change the existing generic `shift_hours` contract, which permits other same-day hours.

**Non-goals for this stage:** implementing code, NiceGUI screens or UI wiring, authentication, deployment, payroll, forecasting, legal compliance, breaks, overnight or fractional shifts, availability, skills, and publication. This spec may define data that a future UI needs to show; it does not define controls or visual layout.

## 2. Functional requirements

### FR-1 — Schedule lifecycle and isolation (BR-01)

1. A schedule represents one typical week ordered Monday through Sunday, with 16 one-hour operating buckets per day, `[07:00, 08:00)` through `[22:00, 23:00)`. It is not tied to the historical CSV dates.
2. Creating a schedule uses the existing trimmed, nonblank, at-most-100-character name rule, allows duplicate names, and creates independent defaults: shift definitions 07:00–15:00 and 15:00–23:00; threshold `N = 20`; daily shift limit `1`; no staff, demand, or assignments.
3. The service can identify, list, and rename schedules by stable ID. Mutations and reads are scoped to one schedule ID; a missing ID is rejected. Renaming uses the same name validation and does not change child data.

### FR-2 — Staff and weekly capacity (BR-02)

1. Add, edit, and remove staff by stable employee ID. Names are trimmed and nonblank; duplicate names are permitted. The returned record contains its ID so names need not be unique identifiers.
2. Weekly maximum hours are finite, nonnegative, whole hours at or below `2^31 − 1`. Boolean, fractional, negative, nonnumeric, NaN, infinity, and out-of-range inputs fail validation. Zero is valid and excludes the employee from automatic assignment.
3. Lowering a maximum retains assignments, recalculates utilization, and returns an `OVER_WEEKLY_MAX` warning with assigned hours, limit, and excess. Removing assigned staff requires an explicit confirmed operation; it removes all their assignments in the same transaction and updates derived metrics. Cancellation changes nothing.

### FR-3 — Shift definitions and daily limit (BR-04)

1. Shifts have stable IDs and whole-hour start/end values with `07 <= start < end <= 23`. They apply on any weekday. Exact duplicate time pairs are rejected; distinct shifts may overlap. The end is exclusive, so adjacent shifts do not overlap.
2. Add, edit, and remove shift definitions within one schedule. An edit to a used shift evaluates **all** affected assignments against the proposed times. It rejects any resulting same-person overlap or duplicate definition atomically and identifies affected assignments. If only weekly maximum or daily-limit policy is breached, it succeeds and returns warnings.
3. Removing a used shift requires an explicit confirmed operation; all dependent assignments are removed atomically. A schedule may have no shifts, but generation then returns a prerequisite error.
4. The schedule's daily shift limit is a positive whole number at or below `2^31 − 1`. Changing it preserves assignments and recalculates warnings. Back-to-back shifts count as two shifts, though they do not overlap.

### FR-4 — Transaction CSV validation and import (BR-03)

1. Accept the supplied format, including an optional date-range title line and headers such as `Fri, 07 Aug`, as well as full or abbreviated English weekday names in any column order and case. Normalize to Monday–Sunday. Accept whole-hour labels including `7am`, `7 AM`, `07:00`, `1pm`, and `22:00`; dates in labels are metadata, not a scheduling week.
2. A valid report contains **exactly one** nonnegative, finite, whole-number transaction count at or below `2^31 − 1` for each of the 112 weekday/hour combinations. Zero is valid. Blank, negative, fractional, nonnumeric, non-finite, out-of-range, missing, and duplicate values are errors. Unknown weekday/hour labels and hours outside 07:00–22:00 are errors. Ambiguous or repeated normalized weekday columns are errors. Reject a report whose weekly transaction or required-staff total would exceed the same integer ceiling.
3. Recognizable `Total`, `Sum`, `Grand total`, or `All` rows/columns, title/date-range lines above the header, and entirely empty rows/columns are ignored with **positioned warnings**. Their numeric values never enter demand. Unexpected nonempty data is an error. Return all discoverable findings together with severity and source position, including day/hour for cell errors.
4. Parsing and validation finish before any demand write. Any error or resource-limit failure leaves prior demand, assignments, history, and metrics unchanged. The first valid import stores normalized demand and warnings without generating a roster. A later valid **re-import** is prepared for review; only after explicit confirmation does FR-8 snapshot the prior schedule, replace demand, generate a fresh roster, and return the refreshed result. Cancellation changes nothing. This confirmed re-import behavior overrides BRD BR-03/D-10/INV-15/AT-18.
5. No imported demand is an explicit `unavailable` state, distinct from a valid report containing zeros. A validation result can support a future preview without changing stored data.

### FR-5 — Required-staff estimate and settings (BR-05)

1. For each imported bucket, `required = max(1, ceil(transactions / N))`, where `N` is a positive whole-number transactions-per-person-hour threshold at or below `2^31 − 1`, default `20`. Use integer arithmetic so large valid counts do not cause floating-point errors.
2. Before the first valid import, changing `N` is a settings edit with no roster or history to replace. Once demand exists, a valid change is prepared for review; after explicit confirmation, FR-8 snapshots the prior schedule, applies the threshold, generates a fresh roster, and returns the refreshed result. Cancellation or a failed action preserves the old threshold, roster, demand, and history. `0`, fractional, boolean, nonnumeric, non-finite, and out-of-range values are rejected without mutation. This confirmed-change behavior overrides BRD BR-05/INV-15/AT-19.
3. Required staffing and scheduled staffing are separate outputs. The estimate is a workload proxy, not a service-level or employee-performance claim.

### FR-6 — Unified validation and manual assignment edits (BR-08; Section 7)

1. Adding, removing, and reassigning one employee/day/shift assignment is evaluated against the **resulting state**. Reassignment removes the old assignment and adds the new one as one operation. Valid days are exactly Monday–Sunday; all referenced schedule, employee, shift, and assignment IDs must exist within the same schedule.
2. Each violation has a stable code, severity, readable message, and relevant numeric/reference details. The severity policy is: `UNKNOWN_REFERENCE`, `DUPLICATE_ASSIGNMENT`, `SHIFT_OVERLAP`, `INVALID_SHIFT_RANGE`, and `DUPLICATE_SHIFT_DEFINITION` are errors; `OVER_WEEKLY_MAX` and `OVER_DAILY_SHIFT_LIMIT` are warnings on manual/definition/settings edits and hard constraints during generation. `UNDERSTAFFED` and `OVERSTAFFED` are diagnostics, not blockers. Low utilization is informational.
3. A proposed edit commits **if and only if** it has no error-severity violation. Error-bearing edits leave the complete prior state unchanged. Warning-bearing edits commit and return the resulting warnings. An over-maximum add explains previous assigned hours + added shift duration = resulting hours versus limit.
4. Current warnings and metrics are derived from current data; historical snapshots retain the metrics calculated for the prior state. Removal, reassignment, staff/shift edits, confirmed demand re-imports, and confirmed threshold changes return a coherent updated result. Manual edits may intentionally leave shortages, excess, zero-hour staff, or policy-limit breaches; they may never create dangling, duplicate, or overlapping assignments.

### FR-7 — Deterministic, best-effort draft generation (BR-06; Section 5)

1. Generation requires complete valid demand, at least one shift, and at least one employee who can take an available shift under weekly and daily limits. Missing prerequisites, including a staff list with **no eligible employee**, return a specific error explaining what to re-check and leave the current schedule unchanged. Insufficient *total* capacity after these prerequisites is a valid partial-result case.
2. For each feasible candidate employee/day/shift, calculate the decrease in unmet staff-hours across the **whole shift** and the increase in excess staff-hours. `net benefit = 3 × shortage removed − 1 × excess added` under default policy. Choose a candidate with highest positive net benefit; for equal scores prefer less added excess, then lower current utilization, then fixed Monday–Sunday day order, shift start/end order, and stable shift and employee ID order as the **final** tie-break. Repeat until no feasible candidate has positive net benefit. Do not invent shifts or assign solely to equalize utilization. An optional fairness swap may only preserve coverage, excess, and hard validity.
3. All generated assignments refer to valid records and days, contain no duplicates or same-person overlap, and keep each employee at or below their weekly maximum and daily shift limit. Employees with zero maximum or below-minimum shift capacity receive no automatic assignment.
4. Identical normalized inputs, configuration, and stable ordering yield identical assignments and metrics. The result is an editable draft with required, scheduled, covered, unmet, and excess staff-hours, coverage rate, employee assigned/max hours, and hourly diagnostics. It may retain unmet demand; global optimality is not claimed.

### FR-8 — Regeneration safety (BR-09)

1. Generation into an empty roster may commit directly. Replacing a nonempty roster requires an explicit confirmation signal from the caller after the replacement impact is known; cancel leaves every assignment intact.
2. Confirmed regeneration replaces the entire assignment set in one transaction. Validation, generation, or storage failure leaves the old assignment set intact. Staff, shifts, settings, and demand are unchanged by regeneration. Returned metrics correspond to the committed roster.
3. A valid re-import or post-import threshold change is a separate **confirmed refresh** operation. Before confirmation, validate the proposed input and show the replacement effect without writing. Confirmation must identify the version of the active schedule that was previewed; if it changed meanwhile, reject and require a fresh preview. On confirmation, read the current schedule, store an immutable, schedule-scoped snapshot of its name, staff, shift definitions, settings, complete demand, assignments, and calculated analytics with timestamp and change reason; then apply the proposed demand and/or threshold, generate a fresh draft, and replace the active assignments. The snapshot, setting/demand update, and roster replacement commit as **one transaction**. Return the new roster and metrics for the future UI to replace its displayed draft.
4. A cancelled refresh creates no snapshot and changes nothing. If validation, generation prerequisites, numeric limits, or persistence fail, roll back the entire refresh: no snapshot, new demand/threshold, or new roster survives. A successful refresh creates exactly one prior-state snapshot. Standalone confirmed regeneration follows points 1–2 and does not create a history snapshot unless it is part of a confirmed refresh.

### FR-9 — Coverage and transaction metrics (BR-10)

1. Each one-hour bucket reports imported transactions; scheduled staff-hours equal the number of assigned people whose shift covers the bucket; required staff-hours equal required staff; `covered = min(required, scheduled)`; `unmet = max(0, required − scheduled)`; `excess = max(0, scheduled − required)`. The bucket transaction ratio is `transactions / scheduled` when scheduled > 0, otherwise undefined (`–` at presentation).
2. Weekly scheduled staff-hours and transactions are sums over all 112 buckets. Overall transactions per staff-hour are `total transactions / total scheduled staff-hours` when the denominator is positive. The separate arithmetic average is the unweighted mean of **staffed-cell** transaction ratios. Unstaffed cells still contribute to total transactions. Both ratios are undefined when all staff-hours are zero.
3. Coverage rate is `sum(covered) / sum(required)`, within 0–100%; sum of unmet and sum of excess are reported separately. Employee utilization is `assigned hours / maximum hours` for positive maximums; zero maximum is undefined (`N/A` at presentation). Manual over-limit utilization may exceed 100% and must carry a warning.
4. Sum of employee assigned hours, sum of shift assignment durations, and sum of bucket scheduled staff-hours are equal. Diagnostics identify day/hour, required and assigned staff, and numeric shortage/excess. Without imported demand, transaction-dependent and coverage metrics remain unavailable rather than being represented as zero.

### FR-10 — Layer contracts and persistence (all BRs)

1. `src/domain/` owns pure normalization, validation, estimation, generation, and metric calculations; `src/model/` carries typed records/results; `src/db/` owns parameterized SQLite schema and queries; `src/services/` coordinates validation and atomic use cases. The future UI consumes service results and performs presentation/confirmation, without duplicating business rules.
2. Persist schedule-scoped staff, shifts, settings, complete demand, and assignments in SQLite with foreign-key integrity and explicit transactions. Reads after reopening the service reproduce the same roster and metrics. The existing `ScheduleService.create_schedule` / `list_schedules`, generic time helper, and named-schedule behavior remain compatible.
3. A read result supplies the complete roster grouped by Monday–Sunday and configured shift, with shift ID, start/end times, employee IDs/names, and allocated/max hours. This is the data contract for BR-07; visual layout and interaction belong to a later UI stage.
4. Historical snapshots are immutable records in the existing database/service boundary, keyed by schedule and snapshot ID. Analytics are computed from the captured prior state and never silently recomputed from the active schedule. A later read can list and inspect them; the baseline has no restore or deletion action.

## 3. Non-functional requirements

- **Performance:** On a local machine, pure calculations for a 112-cell week should be effectively immediate. Accepted measurable target: a schedule with 100 employees and 32 shift definitions generates within 10 seconds; import and metrics refresh complete within 1 second for a valid 112-cell report. Measure the confirmed refresh, including snapshot persistence, separately so history writes do not hide a slow path. These are acceptance targets, not measured current performance.
- **Security and input limits:** Treat CSV bytes, all browser-originated values, environment values, and any future external response as untrusted. Validate type, range, length, and schedule ownership before writing. The maximum for every externally accepted, persisted, or returned integer value (including imported counts, settings, IDs, and aggregate totals) is **`2^31 − 1`**. Reject an operation atomically if an input or its resulting integer totals exceed it; use wider intermediate arithmetic to detect overflow safely. Use bounded CSV decoding/parsing with accepted caps of 1 MiB per file, 256 rows, 32 columns, and 4,096 characters per cell. A limit breach is a clear atomic error, not a partial import. Do not execute input, deserialize unsafe formats, trust user-supplied file paths, or build SQL from input. Any file path used by future import plumbing must be resolved and checked against its allowed base directory.
- **Reliability:** Foreign keys remain enabled. One business action commits all related rows or none. Repeated reads and metric calculations do not mutate state. An interrupted import, refresh, or regeneration preserves the prior complete state and history. Confirmed refresh snapshots are append-only and retain the prior full schedule plus hourly and weekly analytics; earlier snapshots are not recursively copied into a new snapshot. No silent exception suppression or logging of uploaded transaction data.
- **Determinism:** Fixed tie order ending in stable IDs; no randomness or dependence on unspecified database row order. Tests compare exact generated assignment sets for identical input and settings.
- **Compatibility:** Python 3.10+, standard library plus current dependencies only. Existing schedule-name and `shift_hours` tests continue to pass. Data migrations must preserve pre-existing named schedules.
- **Error contracts:** Boundary errors identify the invalid field or CSV position and preserve state. Any failure to fit the stated resource limits is distinguished from malformed content. Results expose machine-readable codes and human-readable messages for a future UI.

## 4. Edge cases and failure behavior

| Case | Required behavior |
|---|---|
| Empty schedule, no demand, no staff, or no shifts | Schedule remains valid; generation reports the specific missing prerequisite and does not replace a roster. Missing demand never counts as zero. |
| Zero transactions in a valid open-hour cell | Required staff is one. |
| Blank, missing, repeated, invalid, or out-of-range CSV cell/hour/day | Import reports all discoverable errors with positions; previous demand, assignments, and history remain intact. |
| Summary row/column, date-range title, empty row/column | Ignore with a positioned warning; do not count as demand. |
| Zero or too-small employee maximum | Employee remains; no automatic assignment that breaches the limit; manual assignment may commit with numeric warning. |
| Same-person overlapping shifts versus adjacent shifts | Overlap blocks; boundary-adjacent shifts are allowed, though the daily limit may warn. |
| Used shift edited to overlap versus to exceed weekly maximum | Overlap rejects all changes; policy breach commits with warning. |
| Assigned employee/shift deletion | Cancel leaves state; confirmed deletion removes dependents in one transaction. |
| Valid re-import or threshold change after manual edits | Preview and require confirmation. Cancel preserves all data. Confirm snapshots the prior schedule and analytics, then updates the input and replaces the active roster with a freshly generated draft in one transaction; the future UI displays the returned draft. |
| Schedule changed after refresh preview | Reject the stale confirmation and require another preview; neither history nor active state changes. |
| No employee can take any configured shift | Return a prerequisite error explaining that staff maxima, shifts, and the daily limit should be checked. Preserve the active schedule and history, including on a confirmed refresh. |
| Any application integer or resulting total exceeds `2^31 − 1` | Reject the proposed import, setting, or mutation with a field/total-specific error; preserve active state and history. |
| Raw capacity exceeds modeled requirement but shifts are restrictive | A shortage may remain; report it instead of claiming feasibility from total hours alone. |
| All buckets unstaffed or an individual bucket unstaffed | Corresponding transaction ratios are undefined; no NaN or infinity. Overall coverage is 0% with valid demand. |
| Excess employees in a bucket | Report excess; covered demand and coverage rate do not rise above required demand or 100%. |
| Conflicting reassignment or invalid cross-schedule ID | Reject the whole operation; preserve original assignment and metrics. |
| Storage error or process interruption during a multirow action | Roll back all rows, including a refresh snapshot, for that action; a later read sees the preceding valid state. |

**Property tests / invariants (BRD Section 9.4, INV-01–INV-18, with manager override of INV-15):** Exercise multiple small, varied valid weeks, including overlapping and short shifts, unequal maxima, and scarce capacity. For every generated roster assert valid references/day, no duplicate or same-person overlap, `employee hours <= maximum`, `daily shifts <= limit`, reproducibility, and `sum(employee hours) = sum(bucket scheduled staff-hours)`. For every metric result assert `covered <= required`, `unmet >= 0`, `excess >= 0`, coverage in `[0, 1]`, and finite or explicitly undefined ratios. For each rejected mutation assert active-state and history snapshots before/after are equal, including a fresh database read. For each policy-breaching saved state assert a matching warning; for every proposed edit assert commit exactly when no error violation exists. For each confirmed refresh assert one immutable prior-state snapshot and one coherent new active roster; cancellation and failure create no history. These tests must include all P0 paths even if some P1/P2 UI scenarios remain for a later stage.

## 6. Assumptions

1. BRD `[DECISION]` baseline rules are adopted where the manager has not superseded them. The manager's confirmed-refresh decision supersedes BRD BR-03, BR-05, D-10, INV-15, and AT-18/19 only for valid re-imports and post-import threshold changes. The BRD's P0/P1/P2 labels prioritize implementation; they do not waive core functional requirements here.
2. Imported counts are a single representative historical week, not a forecast or an average of many weeks. Store hours are fixed at 07:00–23:00 daily; shifts and transaction buckets are whole-hour and same-day.
3. The manager accepted the importer and performance caps in Section 3. The supplied sample must fit within them; limit failures remain atomic. The manager chose the `2^31 − 1` ceiling rather than the larger `2^63 − 1` alternative.
4. Day order is Monday–Sunday. For deterministic ties, prior net-benefit, excess, and utilization conditions apply first; then shift start/end, stable shift ID, and stable employee ID resolve the final tie. Deleted and recreated records receive new IDs and thus may alter a future tie outcome.
5. Current warnings are computed from active stored records. Historical analytics are captured at refresh time and remain attached to the immutable prior-state snapshot. A future UI can replace its displayed roster and metrics from the committed refresh response.
6. The BRD's `W_under=4` example is tested by a policy-level generator input or test configuration; manager-facing editing of optimization weights is outside this baseline.
7. A snapshot captures the state **before** the confirmed change, including an already manually edited roster; it does not recursively copy older snapshots. The first demand import and threshold edits made before demand exists do not create history. Snapshots remain locally available until a separate retention/deletion policy is defined; restore is outside this stage.
